## Object TeX

次に、出力形式を考えてみましょう。

元のTeXは、 *DVI*(デバイス独立)形式のみでファイルを出力することができました。 DVI形式は、ファイルが印刷されるメディアのメトリックを定義していません。ページサイズとページコンテンツ全体の左上隅の位置。たとえば、PDF形式でファイルを出力できるTeXエンジンを作成することにしたら、そのようなメトリックを定義する必要があります。したがって、元のTeXエンジンのセットに新しいプリミティブを含める必要があります。そして、これはエンジン自体の拡張です。

それが *Object* TeXです。繰り返しますが、**一方では、それはVirtexのプリミティブセットを備えたプログラミング言語であり、新しい出力要件によって課される新しいプリミティブで拡張されています。一方、それは新しいプリミティブも理解している拡張TeXエンジンです。そして、第三に、Object TeXは完全に新しいタイプセッティングシステムです。**

4番目の手があります。 Object TeX形式は、新しいプリミティブを含む定義、たとえばデフォルト値をメディアメトリックに割り当てる定義を含むプレーンテックスに基づく形式でもあります。

## Aspose.TeX

Aspose.TeXは、Object TeXシステムのAPIにすぎません。

## なぜ新しいTeXがオブジェクトなのですか？

では、なぜシステム名に「オブジェクト」を使用したのでしょうか。その理由は、Object TeX エンジンの実際の出力は出力形式のファイルではなく、中間の *オブジェクト* モデルであり、それがターゲット形式に変換されるためです。


## ネイティブエンジンの制約と、マネージド環境における柔軟性

従来のコマンドライン型TeXディストリビューション（TeX LiveやMiKTeXなど）から、Aspose.TeXのようなマネージド型の.NETライブラリへ移行する際、開発者は「ファイルシステムに依存し、プロセス駆動で実行される環境」から、「柔軟なオブジェクト指向アーキテクチャ」へと、根本的なパラダイムシフトを経験することになります。

以下に、ネイティブエンジンが抱える制約と、Aspose.TeXが提供するマネージド環境ならではの柔軟性を比較・整理します。本内容は、技術ドキュメントや開発者向けガイドとして構成されています。

1. ファイルシステムおよびI/Oアーキテクチャ

**ネイティブTeXの制約:**

- 従来のTeXエンジン（pdfTeXやXeTeXなど）は、ローカルのファイルシステムと密接に結びついています。そのため、ディスク上の物理的なディレクトリを指すファイルパスが必須となります。
- サーバー上でネイティブプロセスを実行する場合、多くの場合、システム上の複数のパスに対して読み取り／書き込み権限を付与する必要があります。もし信頼できない`.tex`ファイルが入力された場合、ディレクトリトラバーサル（不正なディレクトリへのアクセス）や、制限されたシステムファイルへのアクセスを許してしまうという脆弱性につながる恐れがあります。
- 動的に生成されたコンテンツやデータベースに保存されたLaTeXコンテンツをネイティブTeXエンジンで処理するには、一度ディスク上に一時ファイルとして書き出す必要があり、不要なI/Oオーバーヘッドや、後処理（クリーンアップ）の複雑さを招きます。

**Aspose.TeXの柔軟性:**

- Aspose.TeXでは、`IInputWorkingDirectory`および`IOutputWorkingDirectory`インターフェースを利用することで、エンジンと物理的なディスクパスを切り離すことができます。
- 開発者は、ローカルディスクを一切介することなく、メモリ・ストリーム（Memory Streams）、ZIPアーカイブ、あるいは任意のデータソースに対して、シームレスにデータの読み書きを行うことが可能です。

2. エラー処理とサーバー実行

**ネイティブTeXの制約:**

- 従来のTeXコンパイラにおいて、フォントの欠落、未定義のマクロ、あるいは構文エラーが発生した場合、単にプログラムが終了するのではなく、実行が一時停止して対話型プロンプト（インタラクティブモード）に移行してしまうことがあります。これにより、バックグラウンドで動作するWebアプリケーションやワーカーサービスが、応答を停止したまま（ハングアップした状態）になってしまう可能性があります。

**Aspose.TeXの柔軟性:**

- .NETランタイム上で完全に動作するAspose.TeXは、コンパイル時の問題や依存関係の欠落といったエラーを捕捉し、標準的なマネージド例外（`TeXException`）としてスローします。 - 安全なバックグラウンド処理により、クラウド関数、マイクロサービス、バックグラウンドワーカーキューにおいて、不正な形式のドキュメントを適切に処理できるようになります。具体的には、サーバーのスレッドを占有（ロック）することなく、エラーのログ記録や、適切なHTTPステータスコードまたはエラーメッセージの返却が可能となります。

3. 同時実行性とスレッドセーフティ

**ネイティブTeXの制限:**

- 標準的なCLIツールは、単一インスタンスでの逐次実行を前提に設計されています。複数のインスタンスを同時に実行するには、OSレベルで個別のプロセスを立ち上げる必要があり、計算コストが高く、高負荷時のスケーリングも困難です。

**Aspose.TeXが提供する柔軟性:**

- Aspose.TeXでは、組版ジョブが独立した`TeXJob`および`TeXOptions`オブジェクトインスタンス内にカプセル化されています。そのため、開発者はマルチスレッドの.NET環境において、複数のドキュメントを同時に処理することが可能です（ただし、オブジェクトインスタンスに関する一般的なスレッド分離のルールに従う必要があります）。
